# 第二批：配置保存与生效状态

基于第一批提交 `ccf28cf` 继续改进，保留 Go、WinDivert 依赖和现有配置文件字段。

## 问题与行为

- 原先直接覆盖 JSON 文件；现在先写同目录唯一临时文件、同步并关闭，再替换目标，失败时保留旧配置。Windows 共享/锁定/访问冲突最多重试 5 次，累计等待最多 150 ms。
- 多个请求保存时，文件替换与内存配置发布现在按同一顺序提交，避免最终磁盘与内存配置不一致。
- Runner 只记录本次运行配置，不再用启动前捕获的旧值覆盖已保存配置。状态接口分别提供 `config`、`runningConfig` 和 `configPending`。
- 页面区分已保存和已生效，支持同步其他页面的保存结果，并保留本页未保存的编辑。应用其他页面已经保存的配置时，不重复提交本页表单。
- API 拒绝空配置、TTL=0、不支持的模式和日志级别；无效输入不会写入文件。旧文件加载的默认值兼容行为保留。

## 验证

Windows amd64、Go 1.27.3；race 使用 LLVM-MinGW 20261006 / Clang 23.1.3。

- 51 项 Go 顶层测试及 fuzz 种子测试通过。
- `go test -race ./...`、`go vet ./...` 通过。
- 前端 11 项测试通过。
- `build.ps1` 通过，产物 `ua3f-win.exe` 为 7461888 字节。
- 24 个并发保存完成后，磁盘与内存配置一致；短暂 Windows 读锁释放后保存成功；只读文件保存失败保留原内容且不泄漏临时文件。
- 启动前捕获旧配置、启动期间保存新配置两类场景均保留新保存值，并正确报告待应用状态。

浏览器使用临时服务器和模拟句柄进行双页面验收：先运行 TTL=64，通过 API 保存 TTL=65，页面显示“当前 TTL 64”及待应用提示；点击应用后，状态接口确认已保存 TTL=65、运行 TTL=65、`configPending=false`。另一个页面未保存的 TTL=66 在轮询和重启后始终保留。
